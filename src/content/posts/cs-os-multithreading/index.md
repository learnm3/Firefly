## 一、进程与线程

### 1.1 核心区别

| 维度 | 进程 | 线程 |
|---|---|---|
| 本质 | 资源分配的最小单位 | CPU 调度的最小单位 |
| 地址空间 | 独立（隔离） | 共享进程地址空间 |
| 通信 | 需 IPC（管道/共享内存等） | 直接共享内存 |
| 切换开销 | 大（切换页表/TLB） | 小（只需切换寄存器/栈） |
| 崩溃影响 | 进程间隔离 | 同进程线程互相影响 |

**线程共享**：代码段、数据段、堆、打开的文件
**线程独享**：栈、寄存器、线程局部存储（TLS）

### 1.2 游戏为什么多线程

```
游戏线程（GameThread）：逻辑、蓝图、物理（部分）
  ↓ 命令队列
渲染线程（RenderThread）：场景遍历、剔除、渲染命令
  ↓ 命令队列
RHI 线程：提交给 GPU 驱动
```

分工原因：**单线程的帧时间 = 逻辑 + 渲染 + 提交串行**，多线程让它们并行，帧时间大幅下降。UE5 还有 TaskGraph 做细粒度并行任务（动画、物理、寻路）。

> **面试必答**：游戏用多线程把逻辑、渲染、提交并行化——UE 里 GameThread/RenderThread/RHI 线程通过命令队列解耦。**但多线程的代价是数据竞争**，需要同步机制，这就是下一节的内容。

## 二、线程同步方案（重点）

### 2.1 四种方案对比

| 方案 | 原理 | 临界区长短 | 开销 | 场景 |
|---|---|---|---|---|
| **互斥锁（mutex）** | 阻塞等待，让出 CPU | 长 | 中（系统调用） | 任务队列、共享数据结构 |
| **自旋锁（spinlock）** | 忙等轮询 | 极短 | 低但耗 CPU | 极短临界区、多核 |
| **原子操作** | 硬件指令（CAS） | 单变量 | 最低 | 计数、标志、引用计数 |
| **条件变量** | 等待条件满足再唤醒 | 配合互斥锁 | 中 | 生产者-消费者 |

### 2.2 互斥锁（Mutex）

```cpp
std::mutex mtx;
int sharedCounter = 0;

void SafeIncrement() {
    std::lock_guard<std::mutex> lock(mtx);   // RAII：构造加锁，析构解锁
    sharedCounter++;
    // 作用域结束自动解锁（异常安全）
}
```

**关键认知**：锁的粒度决定性能。**持锁时间越短越好**——只锁临界区，不要在锁里做 IO 或复杂计算。

### 2.3 原子操作（Atomic）

```cpp
std::atomic<int> counter{0};

// 无锁：硬件级原子指令（CAS/load/store）
counter.fetch_add(1);           // 原子加
int old = counter.exchange(5);  // 原子交换
```

**为什么原子最快**：直接走 CPU 的原子指令（如 x86 的 `lock xadd`），无系统调用、无上下文切换。适合**单个变量**的场景。

### 2.4 自旋锁 vs 互斥锁（面试高频）

| 场景 | 选择 | 原因 |
|---|---|---|
| 临界区极短（几条指令） | **自旋锁** | 阻塞切换线程的成本 > 忙等的成本 |
| 临界区长（IO、复杂计算） | **互斥锁** | 忙等浪费 CPU，阻塞让出更合理 |
| 单变量计数 | **原子操作** | 连锁都不用 |

**游戏场景**：任务队列（长操作）用互斥+条件变量；每帧更新的计数器用原子；线程池内部极短同步用自旋。

### 2.5 死锁：四个必要条件

1. **互斥**：资源一次只能被一个线程占用
2. **持有并等待**：持有资源的同时等待其他资源
3. **不可剥夺**：资源不能被强行抢占
4. **循环等待**：线程间形成环形等待链

**预防/避免**：

- 破坏循环等待：**统一加锁顺序**（所有线程按相同顺序获取锁）——最常用
- 破坏持有并等待：一次获取所有锁（`std::scoped_lock` 多锁同时加）
- 用 RAII（`lock_guard`）保证异常时也释放
- 工具：静态分析、死锁检测器

```cpp
// 反模式：两个线程以相反顺序加锁 → 死锁
// 线程1: lock(A); lock(B);
// 线程2: lock(B); lock(A);   ← 交叉等待

// 正确：统一顺序
// 线程1: lock(A); lock(B);
// 线程2: lock(A); lock(B);   ← 顺序一致
```

## 三、内存与虚拟内存

### 3.1 虚拟内存与分页

```
进程看到的地址空间（虚拟） → 页表 → 物理内存帧
                                    ↓ 缺页
                              从磁盘换入（页面置换）
```

- **虚拟内存**：每个进程拥有独立的连续虚拟地址空间，按需映射物理内存
- **页表**：虚拟页 → 物理帧的映射表
- **缺页中断**：访问未映射页时触发，从磁盘换入
- **好处**：隔离、可超内存运行、共享库只需一份物理副本

**页面置换算法**：

| 算法 | 思路 | 问题 |
|---|---|---|
| FIFO | 先进先出 | 可能抖动（Belady 异常） |
| **LRU** | 淘汰最久未用 | 需要访问历史，实现贵 |
| **CLOCK（时钟）** | LRU 近似：环形链表+引用位 | 硬件友好的折中 |

### 3.2 内存对齐与缓存行（性能核心）

```
CPU 访问内存以缓存行（Cache Line，通常 64 字节）为单位
数组连续存放 → 一次加载 64 字节覆盖多个元素 → 缓存命中
链表节点分散 → 每次访问都可能未命中 → 从主存重新加载（慢 ~100 倍）
```

**游戏数据导向设计（DOD）**：把对象拆成"结构数组（SoA）"，按帧遍历时数据连续 → 缓存友好。这就是 ECS 的核心动机之一。

## 四、伪共享（False Sharing）：多线程性能杀手

### 4.1 问题

**不同线程修改同一缓存行内的不同变量 → 缓存行在两个核心间反复失效 → 性能雪崩。**

```
缓存行（64 字节）：[ 线程A的countA | 线程B的countB | ... ]

线程A 改 countA → 缓存行标记脏 → 线程B 的 countB 也失效
线程B 改 countB → 缓存行标记脏 → 线程A 的 countA 也失效
→ 两个线程互相"踢"对方的缓存，每次修改都要重新从主存加载
```

### 4.2 解决：填充对齐

```cpp
struct alignas(64) PerThreadData {   // 对齐到缓存行边界
    int32 Count;                      // 每个线程的数据独占一个缓存行
    // 填充到 64 字节，避免与其他线程共享缓存行
    char Padding[60];
};
```

**游戏场景**：多线程任务系统里每个线程的私有统计、并行粒子系统的每线程状态。

> **面试必答**：伪共享是不同线程的变量恰好落在同一缓存行导致的缓存行反复失效——虽然变量逻辑上无关，物理上互相干扰。解决方法是**把变量对齐到独立缓存行**（`alignas(64)` + 填充）。这是多线程性能优化的经典考点。

## 五、对象池与内存池（游戏高频）

### 5.1 为什么游戏需要池

子弹、特效、伤害数字——**高频创建销毁**的对象，直接 new/delete 的问题：

1. **分配开销**：每次走分配器（找空闲块）
2. **内存碎片**：频繁分配释放导致碎片化
3. **缓存不友好**：对象分散在堆里，遍历时缓存命中率低

### 5.2 实现

```cpp
template <typename T>
class ObjectPool {
    std::vector<T> pool_;              // 预分配，连续内存（缓存友好）
    std::vector<int> freeIndices_;     // 空闲索引

public:
    explicit ObjectPool(int capacity) {
        pool_.reserve(capacity);
        for (int i = 0; i < capacity; i++) freeIndices_.push_back(i);
    }

    int Acquire() {
        int idx = freeIndices_.back();
        freeIndices_.pop_back();
        return idx;                    // 复用内存，不重新分配
    }

    void Release(int idx) {
        freeIndices_.push_back(idx);
    }
};
```

### 5.3 池化 vs 直接分配

| 维度 | 直接 new/delete | 对象池 |
|---|---|---|
| 分配开销 | 每次都有 | 仅初始化一次 |
| 内存碎片 | 有 | 无（固定块） |
| 缓存局部性 | 差（分散） | 好（连续） |
| 实现复杂度 | 简单 | 需管理空闲列表/状态重置 |

**UE 中的体现**：Actor Pool、引擎级内存分配器、GAS 的 GE 池化等。
